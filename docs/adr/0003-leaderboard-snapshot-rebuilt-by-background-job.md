# 榜单快照由后台作业重建，请求路径只读

排行榜没有复用仪表盘统计的缓存模式（请求触发、stale-while-revalidate、进程内 CAS 单飞），而是由一个 leader lock 保护的后台作业每 5 分钟用一条 SQL 同时算出三个窗口的按用户聚合，写入 Redis；HTTP 请求路径只读快照，快照缺失时返回「正在计算」，永不触发聚合。原因是这次聚合要扫原始 `usage_logs`（现有索引对「整窗口、全用户」的 GROUP BY 帮不上忙，本月窗口约占全表三分之一），面向的是全体登录用户而非单个管理员页面；挂在请求路径上意味着冷启动和 key 过期时的并发请求各自跑一次整月扫描，而仪表盘那套单飞是全 service 一个 int32、跨实例无效。管理端仪表盘当年正是为了避免全表扫描才引入预聚合表，排行榜不应把这条路重新走一遍。

## Considered Options

- 请求触发 + 双 TTL + 进程内 singleflight + Redis 刷新锁：可行但要同时补四个机制才能正确，否决。
- 直接建按用户 × 天的预聚合表：未否决而是延后，上线前用生产量级数据实测月窗口聚合，达到秒级即建表。

## Consequences

- 快照只含 user_id 与数值；展示名和参与资格在响应时按 users 表当前状态渲染，所以下架即时生效。不设禁用 / 删除 / 切换模式时清空快照的钩子：清空不会让任何事更早生效，只会让全站在下一轮重建前看到「正在计算」。
- Redis key 带窗口起点，TTL 到窗口结束，跨零点、周一、月初旧 key 自然作废。
